# Knowledge connections beyond recorded edges: evaluation

Status: pure layer and main-process wiring built and measured on a fixture (2026-11-05). Nothing here ran against real
engagement data, a live model or the app. Companion to `docs/design/knowledge.md`. Code: `src/shared/knowledgeIndex.ts`,
`src/shared/knowledgeLinks.ts`, `src/shared/knowledge.fixture.ts`. Sections 2 to 5 are pinned in
`src/shared/knowledgeLinks.test.ts` ("evaluation on the fixture"; `npx vitest run src/shared/knowledgeLinks.test.ts`).
Section 6 is pinned in `src/main/runtime/knowledgeRecall.measure.test.ts` ("pins the sizes", the dedupe test); the tokens
there are an estimate. Section 8's timings are logged by that file and by `src/shared/knowledgeMatcher.adversarial.test.ts`:
they are one machine's numbers, asserted only as generous limits, never pinned.

## 1. Question

An engagement graph holds what the team recorded as edges. A consultant also wants connections nobody recorded:
"this risk names that system", "these two entries are the same thing". Which of those can OrgAI derive without a
model, show as a suggestion the user confirms or dismisses (never as a stored edge or fact), and, for the strongest
kind, hint to agents in a recall? And which should stay relations that agents record with judgement?

Rules for a candidate to ship:

1. Precision on the fixture is high enough for the audience: at least 0.9 for anything shown to an agent, at least 0.6
   for a suggestion the user can dismiss with one click.
2. Confirming it makes sense: it becomes an ordinary user edge, so there must be a relation word worth recording.
3. It is not already visible elsewhere in the UI.
4. The volume stays reviewable, and the cost has a fixed ceiling whatever an agent writes (section 8). The first matcher
   was called linear and was not: its cost grew with the number of names sharing a first word.

## 2. The fixture, and why it is a weak test

`knowledge.fixture.ts` is a fictional engagement (Quill & Rowe moves Halden Freight's invoicing from a legacy system to
Stripe): 71 entities (69 live, 2 retired), 102 relations (1 retired), retired facts, five context notes. It was written
with traps: a person William Okafor with the alias Bill and prose about "the bill run"; a person with the alias Mark and
the verb "mark"; a team Finance and lower-case "finance" in prose; a system Atlas, an organisation Atlas Freight with the
alias Atlas and "an atlas of processes"; Stripe as organisation and system; "Core" inside "Billing Core" plus a
subcontractor with the alias Core; "VAT per line" as both a requirement name and everyday phrasing; a client organisation
named by many entities; and a catch-all context note linked to nine unrelated entities.

Ground truth is the author's intent: in the fixture text `{Surface|Entity}` marks a reference the author meant
(113 of them, 111 between live entities), and a name without braces is a deliberate non-reference. Two weaknesses:

- **The same people wrote the fixture and the matcher.** Precision measured here does not predict precision on real
  data. Real engagement text has typos, pronouns, abbreviations and names the author never thought of.
- **I corrected labels after the first look.** The first run showed false positives that were my own omissions (eight
  references to "Halden" without braces, two sentence-start references I had described but not marked), so I fixed the
  fixture, not the matcher. Three behaviours then changed because of what that first run showed (section 4.1: the
  owner-span rule, the ambiguity penalty, no hub limit on mentions). The numbers below are after those changes, so they
  are fitted to this fixture to that degree.

The same-target and shared-note usefulness labels are my own hand judgement (listed in the test). They are opinions.

## 3. Method

Each candidate generator ran on the fixture. "Correct" for mentions means the pair is in the author-marked truth. For the
others the labels are in the test (`SAME_TARGET_USEFUL`, `SAME_NAME_USEFUL`, the incidental-note flags). Candidates that
were rejected are generated by helpers inside the test file and are not shipped code.

## 4. Candidates

### 4.1 Mentions (an entity's summary or live fact names another entity)

- Meaning to a consultant: "this risk is about that system", "this decision involves that person". It turns prose that
  agents already wrote into navigable links, and it feeds the size of graph nodes.
- Signal: the shared name matcher (`knowledgeNameMatcher`, a token trie) over summaries and live facts. Word boundaries
  come from tokens, the longest name wins at a position, names under 3 characters are skipped, a name inside another name
  is consumed ("Billing Core" never also yields "Core"). A name of more than 8 tokens is not matched as a mention, and a
  span matches at most 16 entities (section 8). Neither moved a number below: no fixture name reaches those limits.
- Case and common-word rule: a single-word name must be spelled with its own capitalisation, and a single-word name from
  `KNOWLEDGE_COMMON_WORDS` (mark, bill, will, may, core, plan ...) is also refused at the start of a sentence. Multi-word
  names ignore case.
- Measured on all 129 mention links the matcher produced (every mention, before any edge filter):

| rules | links | correct | precision | recall (of 111) |
| --- | --- | --- | --- | --- |
| shipped (case rule + common-word guard) | 129 | 109 | 0.845 | 0.982 |
| no case rule | 136 | 109 | 0.801 | 0.982 |
| no common-word guard | 135 | 111 | 0.822 | 1.000 |
| neither | 141 | 111 | 0.787 | 1.000 |

  The case rule removes seven links, all false (the lower-case traps in the fixture). The guard removes six links, four
  false and two true: a fact that starts "Bill confirmed ..." and one that starts "Mark agreed ...". That recall loss is
  real and accepted. The 0.845 headline is dominated by ambiguity,
  not by the traps: a span that names two entities (Stripe organisation and system, Atlas and Atlas Freight, Core and
  Core Logistics) links to both and one is wrong.
- Strength is `0.35 + 0.15 * min(count, 3) + 0.2 if the name has several words`. When every backing text was ambiguous it
  is that minus 0.3, and never more than 0.49 however often the name repeats. Measured by strength: at least 0.5 is 95 links with 93 correct (0.979); at least 0.65 is 62 links with 60
  correct (0.968); below 0.5, the ambiguous ones, 34 links with 16 correct (0.471).
- What the user would see: pairs without a recorded edge (a retired edge an agent wrote does not count, or an agent could
  silence a suggestion by linking and retiring; a retired edge the user wrote does). Unambiguous suggestions: 40 links, 38
  correct (0.95). The two false ones are the phrase "VAT per line" appearing in ordinary prose ("calculates VAT per line
  item"), a case no case rule can catch (asserted in the test by the name of their target). Ambiguous mentions are counted in appearances but never suggested.
- Strong mentions for agents: `KNOWLEDGE_STRONG_MENTION = 0.65` (a name of several words, or the same name in two or
  more texts, and unambiguous). Without edges: 21 links, 19 correct (0.905), over the 0.9 bar by one link; the two misses
  are the VAT phrase. I chose 0.65 because it is the structural line (several
  words or repeated), not because it was the best cut: the fixture cannot tell 0.5 (0.979) from 0.65 (0.968), and I kept
  the stricter one because a wrong pointer costs an agent tokens and trust while a missing one costs nothing.
- Hub cutoff: dropping mention suggestions whose target is named by more than N entities did not help. Suggestions and
  correct: none 40/38 (0.95), N=12 33/31 (0.939), N=8 27/25 (0.926), N=4 22/20 (0.909). It only removes true links.
  So mentions are not hub-limited by default (`hubCutoff` is an opt-in); the cap of 500 bounds the volume. Whether a
  client organisation named by 1,500 entities crowds the 500 cap is unmeasured.
- False-positive risk beyond the fixture: names that are common phrases; nicknames; pronoun reference (never found);
  non-Latin text (a CJK run is one token, so a name inside a longer run is not found); stored names that are short.
- Token cost: a `~ names: X (inferred)` line is about 12 tokens; at most 3 per entity in a recall.
- Confidentiality: the evidence is text from the same engagement's graph. Shown to the user and to agents of that
  engagement only.
- **Verdict: Build as inferred** (user list: unambiguous mentions; agent recall: strong mentions only).

### 4.2 Shared source (two entities link the same context note)

- Meaning: "both came up in the audit call".
- Signal: equal `noteIds`.
- Measured, pairs without an edge, by hub cutoff on the note's entity count (pairs / useful): 4: 0/0; 6: 25/25; 8: 44/44;
  12: 72/44 (0.611); 40: 72/44. The 100% at 6 and 8 is by construction: I flagged the nine links of the catch-all note as
  incidental and gave it a size above 8. A real catch-all note can be any size, so the cutoff is a guess, and the pair
  count grows with the square of the note's size.
- Why reject, even at 100%: the note is already visible on each entity (its Notes links), the confirm action has no
  relation word (what is the edge between a person and a system that were in the same call?), and 44 pairs from five notes
  would nearly double the suggestion list, which is 45 links (40 mentions and 5 same-name).
- Token cost: none (not built). Confidentiality: same engagement.
- **Verdict: Reject.**

### 4.3 Same target by the same relation (colleagues, shared exposure)

- Meaning: two people `works-at` one organisation; two risks `affects` one system.
- Measured, pairs without an edge, by hub cutoff on the group size (pairs / useful): 4: 27/21 (0.778); 6: 36/21 (0.583);
  8, 12, 40: 49/21 (0.429). The hub (seven people at the client, five decisions by the sponsor) is what ruins it; the
  same 21 useful pairs appear at every cutoff, so a small cutoff costs nothing here, but that is the fixture's shape.
- Why reject: the relationship it implies ("both depend on Ledgerline") is a traversal from the shared entity (its
  neighbours), not an edge between the siblings, and a user confirming it has no relation word to record. The
  neighbours are already in a recall of the shared entity.
- **Verdict: Reject.** Not built; the generator is in the test.

### 4.4 Possible duplicates (equal name or alias across different kinds)

- Meaning: the same thing recorded twice ("Risk review" as a meeting and as a document), or two things sharing a word
  (Atlas the system, Atlas Freight the competitor).
- Signal: equal folded name or alias, different kinds, groups of at most 6, no existing edge.
- Measured: 5 links, 3 useful (0.6): "Risk review", "Kickoff workshop", "Steering committee 3" (a document and the meeting
  it belongs to) are worth linking; Atlas and Core are not. With five samples this is an anecdote, not a rate.
  Stripe organisation and system do not appear because the team already linked them.
- Confirm action: an ordinary edge (the user picks the word), or dismiss. A merge is not offered.
- Token cost: none for agents. Confidentiality: same engagement.
- **Verdict: Build as inferred**, shown to the user only, at strength 0.6 (below strong mentions).

### 4.5 Same run or same agent provenance

- Signal: nodes written by the same run.
- Measured: 550 same-run pairs (runs 1 to 4), 55 related by an edge or a marked mention (0.10); of the 506 pairs with no
  edge, 11 related (0.022). A run writes many unrelated things.
- **Verdict: Reject** (noise).

### 4.6 A suggested relation word from the kinds of the two ends

Measured on the marked mentions the matcher found, against the edge the team recorded in the same direction. This is the
best case: it only covers pairs that already have an edge, and in the real list those pairs are filtered out.

| from > to | mentions | edge recorded (same direction) | table word correct | reversed edge | shipped |
| --- | --- | --- | --- | --- | --- |
| person > organisation `works-at` | 14 | 14 | 14 | 0 | yes |
| risk > system `affects` | 9 | 8 | 8 | 0 | yes |
| system > system `depends-on` | 8 | 4 | 4 | 4 | no (direction is a coin flip) |
| decision > system `affects` | 7 | 2 | 1 | 0 | no |
| decision > person `decided-by` | 4 | 1 | 1 | 0 | no (the other three name the proposer, the raiser and a party agreed with) |
| document > decision `evidence-for` | 1 | 1 | 1 | 0 | no (n=1) |
| open-question > person `can-answer` | 3 | 0 | 0 | 3 | no (the edge points the other way) |

The two shipped rows agree with the recorded edges because I wrote both from the same idea. The suggestion is a word
the user can change on confirm.

- **Verdict: Build for the two pairs; everything else is an agent-recorded relation** (`KNOWLEDGE_COMMON_RELATIONS`).

### 4.7 Judgement connections

Temporal order and supersession between decisions, contradiction between facts, decision-to-evidence, risk-to-mitigation,
question-to-who-can-answer, owner-of. I measured only the kind-pair word above; I did not test a heuristic for the
others. The reason is the table: the kinds say little about direction or role (decision > person was decided-by once and
proposer, raiser and agreed-with three times), and contradiction and supersession need a reader. A heuristic would also
write a claim ("contradicts") into the user's graph on a guess.

- **Verdict: Agent-recorded relation only.** The names stay in `KNOWLEDGE_COMMON_RELATIONS` (supersedes, contradicts,
  evidence-for, mitigates, can-answer, decided-by, owns). Not measured.

### 4.8 Across engagements for the same client

- **Rule: no data from another engagement ever reaches a run or a view of this one**, whatever the client. Engagements
  are the confidentiality boundary (a client may be the same, the contract and the people are not). No function in
  `src/shared` takes more than one graph.
- **Verdict: Reject.** Stated as a rule, not measured.

### 4.9 Transcript co-occurrence and embeddings

- Co-occurrence in run transcripts: transcripts are large, untrusted model and tool output; the signal is noisy
  (everything co-occurs in a long run) and it would reach into other runs' text. Embeddings: a new dependency or a model
  call per entity, cost per graph revision, and text sent out of the machine for a feature that must work token-free.
- **Verdict: Reject** for both. Not measured.

## 6. Does recall beat the keyword search it replaces?

On the five questions in `KNOWLEDGE_FIXTURE_QUESTIONS` (one `knowledge_recall` of the question at the default 1,500
character budget, against the old keyword search with a single word): the expected entities appeared in 16 of 16 places in
the recall text and in 14 of 16 of the keyword hits (4 to 12 entities listed per question, not their neighbours or
facts). This compares different things: recall also prints facts and neighbours, search lists entities, so the 14/16 is
not a like-for-like score. The size comparison against the real vocabulary + search + get output is in
`src/main/runtime/knowledgeRecall.measure.test.ts`: 3,391 to 5,400 characters in 5 or 6 calls against 1,046 to 1,486
characters in one call, every expected name present, on the same fixture and with the same caveats. Tokens were not
measured (about 4 characters per token would put a recall at 262 to 372 tokens: an estimate).

The first version filled the budget whatever the match quality, so a repeated question came back nearly as large (1,490
to 1,480 characters) with ever weaker matches. `KNOWLEDGE_RECALL_RELEVANCE_FLOOR` (0.2 of the best score) now gives detail
only to real matches and names the rest on the "N more:" line, at most 8 names. A repeat at the default budget is now 470
to 930 characters. It was 383 to 806 before "already shown" was limited to entities printed in full and its line gained
"(fresh: true shows it again)": the honest version costs about 100 more characters. Asked about one name, an entity whose only link is a fact naming it is below the floor and is named, not
detailed; that trade-off is untested beyond this fixture.

## 7. Open and unverified

- Everything above is the fixture. No real engagement, no live model run, no app run.
- `KNOWLEDGE_COMMON_WORDS` is a short English list written by hand; other languages and unlisted names (a person named
  "Grant" at the start of a sentence is refused only because it is in the list).
- The edge cases of the matcher on non-Latin scripts are tested for tokenisation only.
- Crowding of the 500-link cap by a very large hub is unmeasured.
- A graph with more text than one pass may scan: the user's own entities are scanned first and each entity may spend at
  most its even share of `KNOWLEDGE_MATCH_BUDGET` (at least 20,000 units), so an agent's early text cannot starve the
  later entities. Past budget / 20,000 (200) entities the floor lets the sum pass the budget and the agent-written tail
  goes unscanned (`partial` says so; nothing is wrong, only missing). Pinned numbers did not move (names at the token cap:
  199 of 2,000 entities scanned before and after).
- The automatic context block matches only user-created entities, by their stored name, and prints a relation only when
  the edge and the other end are user-written (else "+N relations"). Aliases carry no provenance, so none is matched.
  Cost: on a graph mostly written by agents the automatic block rarely fires, and agents call `knowledge_recall`
  (which finds agent-written entities too, marks their text `fact (agent):` and fences it). An agent-created entity an
  agent mentions in a spawn brief gets nothing automatically.
- A recall on a graph of 8 MB or more ranks on a revision up to 30 s old: it can say "Nothing matches" for an entity just
  written (the answer ends "(Search index up to 30 s old.)"); inferred links dismissed since are left out.
- The renderer (confirm, dismiss, node size) and the adapters' calls to `knowledgeContext` and `knowledgeBrief` land
  separately.

## 8. Cost under attack, and on a full graph

Agents write names and text with no card, and one reading a hostile client document may write what it read, so the matcher
has to hold up against text chosen to hurt it. It runs synchronously on the main thread.

**The attack** (review H2, `knowledgeMatcher.adversarial.test.ts`): within one run's 500 writes, 500 entities whose name and
10 aliases are "a a a ... a zN" (120 characters), each with 50 facts of 1,000 characters of "a a a ...". Nothing ever
matches.

| matcher | one fact | whole inference pass |
| --- | --- | --- |
| first version (map first token -> candidates) | 2,672 ms | killed by `timeout 120` still running (by arithmetic 25,000 facts x 2.7 s x 2 passes, about 37 hours) |
| token trie, 8-token cap, budget | 0.1 ms | 40 ms |

The cap alone wins here (these names are over 8 tokens, so they are not in the trie). The worst case left is names at exactly
8 tokens, so every position walks the full depth: 2,000 entities x 11 names x 50 facts stops at the budget in 241 ms, having
scanned 17 entities.

**The limits**: a name of more than 8 tokens is not matched as a mention (it stays searchable and resolvable by name); at most 8
characters of separators between two words of a name; at most 16 entities per span (past that a span is ambiguous and never
suggested anyway); a pass spends at most `KNOWLEDGE_MATCH_BUDGET` (4,000,000 units: tokens scanned, trie steps, matches; a new
pair counts 8). Past the budget the pass stops and `KnowledgeInferredResult.partial` says how many of the entities it scanned.
The cost of a pass is at most tokens x 8 trie steps plus the matches, and the budget caps that total. The precision numbers
did not move: every mention row of section 4 is unchanged by the rewrite.

**A full graph** (`KNOWLEDGE_MEASURE_FULL=1`, one Windows machine, logged, never asserted). The review's 2,000 entities x 50 facts
of 1,000 characters is 106.9 MB of JSON, so it cannot exist: the store refuses past the 64 MB file cap. The largest graph that
fits at that shape is about 1,100 entities (58.8 MB).

| 1,100 entities x 50 facts x 1,000 chars, 58.8 MB | ms |
| --- | --- |
| build the text index (first search or recall after a write) | 2,106 |
| inference pass (stopped by the budget at 276 of 1,100 entities) | 299 |
| substring fallback on a miss: first / later (folded text memoized per index) | 414 / 14 |
| store: cold read / one agent write (parse, clean, stringify, atomic rename) | 211 / 379 |

The everyday case is far below this: 2,000 entities, 5,000 relations, 2.2 MB: index 62 ms, inference 64 ms once, cached read 0.4 ms.

**What this means per write.** Each write makes a new graph object, so the next recall would rebuild the index and the inference.
Under 8 MB of file that stays: scaling the two measurements above puts the rebuild at about 130 ms at 2.2 MB and about 0.4 s at
8 MB (scaled, not measured at 8 MB). At 8 MB or more, `readRecallView` debounces: a
recall ranks on and takes its inferred links from the same revision for 30 s, so an entity written in that window is not found by
a recall until it passes. Printed text always comes from the current graph, and a hit since retired or removed is dropped. Search
(`engagement_knowledge search`) stays exact, so a search right after a write on the largest graph still costs about 2 s on the main
thread, and each write about 0.4 s: slow, not a hang, and only at a size no fixture has come near. Moving this work off the main
thread is the real fix and is not built. The two mention passes were merged into one, the read cache is capped at 96 MB of file size
as well as 4 graphs (the newest always stays), and the substring fallback's folded text is memoized.
