# OrgAI architecture

OrgAI is an Electron app built with electron-vite and three processes. The main process (src/main) holds the runtime adapters, run manager, connections and model catalog, MCP servers and secrets, usage tracking, setup service, worktrees and JSON stores. The preload (src/preload) exposes window.orgai. The renderer (src/renderer) uses React 19 with React Flow and zustand. IPC types live in src/shared/types.ts. Two provider adapters exist: Claude (Claude Agent SDK) and Codex (`codex app-server`). They are reached through three connections: Anthropic, OpenAI and LiteLLM.

The UI overhaul's shell pass and its parallel restyles have landed (docs/design/plan.md, spec.md). The shell is built on native elements with container queries: components/layout, components/ui primitives, top-level project tabs, and a theme layer driven by AppSettings.appearance. Radix Primitives and react-resizable-panels were not adopted (Role.skills has since landed through the skills runtime, #11). plan.md still lists them, so they remain a possible later step. Items below marked PLANNED do not exist in the code.

## Stack

- TypeScript (tsc 7, separate node and web tsconfigs, no baseUrl)
- Electron 45 + electron-vite 6 + Vite 8
- React 19, @xyflow/react 12 (React Flow), @dagrejs/dagre, zustand 5, react-markdown + remark-gfm
- ink 8.0.0 (terminal UI, `src/cli/tui/`, its own `out/cli/tui.mjs` chunk) and ink-testing-library 4.0.0 (its tests), exact pins
- lucide-react 1.64 (SVG icons that take their color from currentColor)
- Plain CSS with custom-property design tokens (no CSS framework)
- @anthropic-ai/claude-agent-sdk 0.3.312 (Claude adapter), zod 4 for harness tool schemas
- @openai/codex 0.166.0 (Codex adapter and the OpenAI connection: `codex app-server`, JSON-RPC over stdio)
- vitest 3 (node env) for unit tests; playwright-core Electron driver for e2e
- electron-builder (Windows nsis + portable tested; mac dmg and linux AppImage configured, untested)
- Node >= 22, git (worktree isolation)
- Not installed (plan.md keeps them as a possible later step): radix-ui, react-resizable-panels. The frontend-design skill is not vendored in .claude/skills.

### Runtime core (provider-neutral)

- Adapter interfaces and the run manager. RunManager picks the adapter, resolves the connection and MCP servers per run, and handles approvals, proposals, questions, merges and MCP install cards.
- Harness tools, each with an audience: 'root', or 'spawners' for the MCP tools. Callers pass a HarnessToolCaller when they know the calling agent.
- Role prompts, activity strings, permission scopes, agent handles and messages, the continuation driver, WorktreeIntegrator and git worktree commit/merge.
- Vendor-neutral usage mapping.
- Image attachments. attachments.ts sanitizes untrusted pasted images: count and size limits, base64 checks, and magic-byte sniffing.
- Run end. activity.ts runOutcome maps how a run ended to finished, stopped or failed, and settleAgent relabels agents Finished, Stopped or Failed (TERMINAL_ACTIVITY). pendingCards.ts cancels the run's open cards at the same point.
- Agent tree rules. agentTree.ts resolves a reported agent's parent without creating cycles and repairs cyclic stored records.
- Concurrency. Skill files that look private (dotfiles, `.env*`, `*.pem`, `*.key`; `dropPrivateFiles`) are left out with a note. These are pattern checks, not a guarantee: a secret in an ordinary-looking value, or a short one under a harmless name, can pass, so the export note tells people to read the file before sharing it. Import applies the same checks to servers and preset variants plus the outside-source rules (https only, no localhost or private-network literal, `reviewTarget` limits, no run-changing or routing secret slot names such as NODE_OPTIONS or Host); the template chart is rebuilt from the parsed roles (known fields, no ids or grants) and the preview carries each role's prompt and elevated tools. - Paths come only from main's own dialogs: `kit:export` takes a path the same renderer picked with the save dialog (consumed by a successful export), the import channels a path it picked with the open dialog (kept for preview and apply). Writes go through a temp file and a rename and refuse a link or folder at the target; reads refuse a link, a non-file and more than 50 MB (O_NOFOLLOW, bounded).
- Import is untrusted input, rebuilt item by item: a bad item is `refused` with a reason (never an error for the file). Skills go through `buildScannedSkill` (shell-injection bodies, name and description rules, caps `SKILL_MAX_FILES` / `SKILL_MAX_FILE_BYTES` / `SKILL_MAX_TOTAL_BYTES`, safe relative paths, no `.git`, no duplicate paths) plus the hidden-character gate on every file; servers through `validateLibraryEntry` plus the preset env / header rules; presets through `validateUserPreset` (saved with `origin: 'kit'`); templates through `cleanTemplateName/Description`, a recursive string scan and `parseOrgExport`. At most 200 items per kind and 500 in all; ids in the file are never used (new `mcpl_` / `skilllib_` / `tpl_` ids).
- Preview classifies each item against fresh state: new, same (identical), different (same name; for presets the same id) or refused, and says whether a replace is possible (a connector or built server of yours is not replaceable). Apply takes `{ path, digest, choices }`, refuses a missing or stale sha256 digest and re-classifies at apply time; only chosen items are applied (`add` for new; `replace` or `copy` for different; `skip`). Items are independent: a failure is listed in `failed` and the rest stay applied. There is no undo. A replace of a server keeps its library id, links and project grants but deletes its stored env / header secret values and sign-in, and each linked project's own values, like an approved retarget; the result lists every imported server with its secret slot names in `needsSecrets`.

### Folder config trust (`src/main/runtime/folderConfigTrust.ts`)

- Ignored saved rules: `listRules` drops rules `readableRule` refuses; `permissions:ignored` (`IPC.permissionsIgnored`, `window.orgai.permissions.ignored(projectId)`) returns them as `IgnoredPermissionRule[]` (`{ rule, reason, hiddenChar?, cut? }`, `listIgnoredRules`, at most 200, rule cut at 1,000 chars, reason is OrgAI's own sentence) and `permissions:remove` deletes one by its exact stored text (hidden characters included; add still never saves one; a `cut` rule cannot be removed that way). Unit-tested only.

- Why: a project folder's own agent config (hooks, env, MCP servers, allow rules) would otherwise apply on the first run, setup included, and OrgAI now fetches foreign code. There is no provenance flag, so a repository cloned by hand is covered too.
- State: `Project.folderConfigTrust` (main-written, `{ state: 'untrusted' | 'trusted', digest?, decidedAt?, importedRules? }`). 'none' = no field (stored before this feature, or no REPO_CONFIG_PATHS entry at creation; deliberately not gated, and a config added later is not noticed), 'changed' = stored 'trusted' whose digest no longer matches. Engagements never get the field. `saveFromRenderer` keeps the stored value and re-judges only on a path change; `cleanFolderConfigTrust` fails closed to 'untrusted'.
- Digest: names, kinds, sha256 of bytes, link targets and (off Windows) the exec bit of everything under 'runs-commands' and 'tools' paths. Regular instruction files and `.orgai/org.json` are shown, not digested, because setup and agents rewrite them; they cannot run or grant anything, and a link in those places is digested. An agent editing a digested file during a run trips the next run. Limits make a config `unreviewable` (accept refused, runs ignore it): 5,000 entries, 64 MB, depth 12, a link leaving the project, a network path, a settings file over 256 KB or a link, a binary under a 'runs-commands' path, any command, target, value or rule over 4,000 chars, a list reaching `FOLDER_CONFIG_LIST_MAX`, a cut text of a 'runs-commands' file. Nothing that would run is cut and then accepted.
- OrgAI's own writes never trip it: a project with the field keeps saved rules in the data folder in every state (`projectRulesLocation`, `appRulesFile`), so `settings.local.json` is digested whole and never written by OrgAI there. The Claude adapter's `updatedPermissions` use destination 'session' only. Accept copies the file's readable rules across (`importedRules`), revoke removes them, a rule the user removed is not re-added, and RunManager leaves them out while the run ignores the folder.
- Run: `RuntimeContext.folderConfigLoads()` is a sticky latch over the folder the run started in. Claude reads it per query build into a per-query snapshot (`cliSettingsLoaded`, so the PreToolUse ask check matches what the running CLI holds); Codex at each launch. Every run kind on the project is covered, with one warn naming the paths ignored.
- Review: `projects:folderConfig` reads from the same bytes it hashes. Values are masked only for display: env and header values whole, in command text only the credential substring (`maskText`), so code around it always shows; `masked` says so, `hiddenChar` flags invisible characters and the text stays unmodified. Writes go through `projects:setFolderConfigTrust`, input rebuilt by ipc.ts `folderConfigTrustArgs`.
- Renderer: Settings > Permissions `FolderTrustSection` (status row plus the review `Dialog`; Allow sends the digest of a review re-read since the dialog opened, a stale digest shows a message and re-fetches), `useFolderTrustReview` (lazy, only a code project with the field), pure logic in `lib/folderTrust.ts`. Pointers to it while agents ignore the folder (untrusted or changed): the New run `FolderTrustNotice` (dismissable per project and digest), a topbar `FolderTrustPointer` on every project view and a `FolderTrustCardLine` on permission cards, all in `components/FolderTrustNotice.tsx`, all opening the review through `openFolderTrustReview`. `.orgai/` files are listed apart as OrgAI team files, since the Team tab's team files gate reviews them. The renderer reads no state the contract does not carry; 'changed' exists only on a fetched review, so surfaces that outlive a view re-fetch on navigation. Verified by unit tests and `e2e/folder-trust.mjs`; UX walks `docs/design/ux-review-clone-start*.md`.
- Checks: `scripts/probe-codex-trust.mjs` (token-free, real binary). `scripts/smoke-folder-trust.mjs` spends tokens, refuses without `--yes`, and has not been run.

### Team files (`src/main/teamFiles/`)

A code project's team lives as plain files under `.orgai/` in its folder, so git carries it between computers. `ProjectStore`'s Project stays a cache that every reader and adapter uses unchanged; the files win, through an approval gate because repository content is untrusted. Contracts: the `// ---- Team files ----` section at the end of `src/shared/types.ts`, channels `TEAM_FILES_IPC`, preload `window.orgai.teamFiles` and `onTeamFilesChanged`.

Layout: `.orgai/team.json` (format `orgai.team/1`, settings: brief, permissionMode, maxBudgetUsd, maxSubagentDepth, maxConcurrentSubagents, maxWindowShare, preferEverydayNearLimit, isolateWriters, reviewMerges, autoContinue, maxAutoContinues, runMessaging, teamReview, skillEvaluation), `.orgai/agents/<slug>.md` (prompt as body; frontmatter name, description, responsibilities, tools, tier or model, effort, canSpawn, spawnable, reportsTo, color, skills, mcpServers), `.orgai/skills/<name>/` (SKILL.md re-emitted with name and description only, plus files; `enabled: false` skills are listed in team.json `disabledSkills`), `.orgai/mcp.json` (format `orgai.team/1`, `servers`, omitted when there are none). Per computer, never in the files: id, path, allowedDirectories, referenceDirectories, provider and tier mapping, keepRuns, setup state, positions, plugins (absolute paths), secrets, OAuth state, connectedAt, buildDigest and built server files.

Design:

- One document. `doc.ts` `TeamDoc` is what parse, serialize, digest, gate and delta all work on. Pure code (parse, serialize, gate, delta, project mapping) is separate from I/O (`disk.ts`, `store.ts`, `service.ts`). Output is deterministic: no timestamps, ids or absolute paths; sorted wherever order has no meaning. The digest covers the parsed document, never bytes (git autocrlf changes line endings); a file is rewritten only when its parsed content differs.
- Three documents per project: the DISK doc (what the folder says now), the APPROVED doc (`<data>/projects/<id>/team-files/approved.json`, the team in use) and the cache (Project, built from approved plus per-computer fields). `state.json` beside it holds lastKnownDigest, rejectedDigest, migrated, removed, dirtyBefore and the last applied / undo records (`undo.json`).
- Gate (`gate.ts`, pure): `gateTeam(approved, disk, { firstSeen })` splits disk's differences into applied at once and pending, and returns the `effective` doc that becomes the new approved. Item by item: prompts, descriptions, removals and lowered power apply; anything raising power stays at its approved value and is listed pending. Tools: the intersection applies, additions pend. So approved moves to effective, and a second gate over the same disk finds only the pending items (idempotent). If the effective doc would be an invalid chart, everything stays at approved and all of it pends. `firstSeen`: everything pends.
- Needs approval: any new or changed MCP launch definition (transport, command, args, env, url, headers, secret names, connector id and variant, `fromLibrary`); a server turned on; a role's effective server access widened (`roles` and the role's `mcpServers` together); added tools; canSpawn turned on or wider spawnable; a new role unless it holds only allowlisted tools (`TRIVIAL_TOOLS` Read, Glob, Grep, TodoWrite; any unknown tool pends) and no canSpawn, skills or servers; a new root or any existing role gaining or losing root-ness (a move under a different parent applies); a higher tier, any pinned model, leaving a tier for anything but a strictly lower tier, or a raised effort ("May spend more"); any new or changed skill (body or files: skills can ship scripts), a skill turned on or a new skill grant; settings that loosen, compared on EFFECTIVE values: a looser permission mode (rank plan < dontAsk < default < acceptEdits < auto < bypassPermissions), isolateWriters or reviewMerges turned off, autoContinue on, runMessaging on, a budget or window share at or below 0 or unset (no cap), depth or concurrency below 1 or unset (the automatic value from the doc's own chart), maxAutoContinues unset (the default), preferEverydayNearLimit ranked true > unset > false, Team review or skill evaluation spending more. Parse refuses depth and concurrency above the real limits. Prompts, descriptions and the brief apply at once as the owner decided, so a pulled prompt reaches the next run without a card (see Risks). Anything else applies at once with one level of Undo.
- Change lists: power first (loosening settings, elevated roles, servers, skills, the rest), at most TEAM_FILES_LIST_MAX. `omittedChanges` counts the rest; approve and create refuse, and `TeamFilesFound.digest` is absent, while anything is omitted, so a digest never approves a change the list did not show.
- Linked servers: `gateTeam` / `describeChanges` take an injected `LinkResolver` (library plus a side-effect-free catalog preview); a linked change shows the ENTRY's real target with `usesStoredSignIn` and `reachesRoles`. A file whose url, command or args differ from the entry makes mcp.json a problem (parse option `linkCheck`). A connector entry added by an apply that fails is rolled back.
- Write through (`ProjectStore.save` hook, so every main-process save counts: projects:save, mcp:*, skills:*, approved proposals, org merges, imports). Main-process saves are the user's or approved actions, so their delta is approved. The hook first ingests the folder if its digest differs from lastKnownDigest, then applies the save's item-and-field delta (`delta.ts` `applyTeamDelta(base, before, after)`) to BOTH the approved doc and the DISK doc, and writes only the files that changed. Writing disk-plus-delta rather than the cache means a pending or rejected change in a file survives a save untouched. A renderer save built from a copy older than an ingest uses the pre-ingest doc as `before` (matched by `Project.updatedAt`, last few ingests kept in memory), so a stale save never reverts a pulled change. A write failure never fails the save: `dirtyBefore` keeps the delta's base and the write is retried at the next check. Nothing is written, and `dirtyBefore` is kept, when the parsed doc is null and the folder holds team content, when team.json is missing from such a folder, or after a failed or too-large read: such a read never overwrites. A delta touching a held file also keeps `dirtyBefore`, and once the file parses again the retry applies it before gating, so the edit is not lost. An empty folder, a fresh repo, or a branch that never had team files still gets a real saved change written (a new untracked set there can block a later checkout of a branch that has them).
- Read: `check(projectId)` at project open (teamFiles:status), window focus (no first write, at most once per 2 s) and run start. A cheap lstat stamp skips parsing when nothing changed; on focus git runs only when the stamp changed or the last answer is 60 s old (an outside `git commit` touches no team file); owners are memoized per pass; `found()` is memoized by stamp and library fingerprint.
- A run's team is fixed at its start. RunManager reads the project once; an approved change reaches the live run only through `setLive(saved, settle, own)`, which overlays just that category, and for servers and skills only the items the proposal or install names (`overlayOwnItems`) and the grants to them. A pull the same save ingested stays out.
- Ids: `mergeOrgChart` keeps role ids per slug, so grants and positions survive; slug, color and effort then come from the file. New roles are laid out automatically.
- Never destructive. No `team.json` or no `agents` folder or an agents folder with no role files: not an empty team, a problem naming it, nothing overwritten by a check. A deleted single role file is a real removal only while team.json and the folder exist. A file that does not parse (conflict markers included) keeps the approved content for that item, is a problem naming the file and is never overwritten; approve refuses until it is fixed. team.json and mcp.json are one unit each; a refused server makes mcp.json the problem.
- Two projects on one folder: the oldest project (createdAt, then id) owns the team files; any other is `off` with `offReason: 'shared-folder'` and neither reads nor writes them.
- Local-only items: a server refused by the credential checks, a built server, is left out of the files with a note and survives ingest (the rule is computed from the spec, never stored); grants to it are kept. Plugins stay local with a note. Private-looking skill files (`.env*`, `*.pem`, `*.key`, dotfiles) are never written (a note in status), dropped on read with a note, and a skill folder rewrite keeps the local copy.
- Secrets across branch switches: a server that disappears from the files keeps its secrets, OAuth and id. `<data>/projects/<id>/team-files/tombstones.json` holds `{ name, id, spec, at }` (at most 200, oldest dropped with its secrets) and the same launch takes its id back through approve, Undo or a switch back. Coming back still pends as a new service, since a removal already moved the approved team. A different launch gets a new id, so stored secrets never follow a retarget. Only an explicit user removal (mcp:remove and the like, which delete a live server's secrets) or the tombstone cap deletes them. `applyDoc` deletes no secrets, and a deleted mcp.json takes the same path.
- Library links: a linked server is written with its definition plus connectorId or `fromLibrary`; another computer links a matching connector or identical library entry, else keeps a project-only copy. Without its secrets it does not start (existing behaviour). Linked skills are written as copies. A library edit is the user's own action: `absorbLinkedSkillEdits` (in `check` and the save hook) moves it to approved and writes it through without the gate, unless the file's own copy already differs. A changed file for a linked skill is a gated change; approving it drops the link and stores the file's copy as the project's own; rejecting keeps the link.
- Hidden characters found in a local value are stripped from the document (never written), with a note; the cache keeps them until the next change. Over-long local values are clamped with a note. A role slug no file can hold (con, aux, nul, com1...) blocks the write with a rename message.
- Shared folder and create path: `projects:checkPath` drops source 'orgai' from `agentSources` while `teamFiles` is set, and `projects:create` drops it from `importAgents` too. `ProjectCreateInput.teamFiles` never stores the default chart. `importAgents` on create stays digest-free: it predates team files and is the user's choice in the form, so it is not gated.
- Git: `commitPaths` (worktrees.ts) stages and commits exact team paths with `--literal-pathspecs`, `--only`, `--no-verify` and `core.hooksPath` off, never pushes, and a file the user staged stays staged and out of the commit. The status call also passes `core.fsmonitor=false`. With uncommitted `.orgai` in the main checkout, a report touching other files or a dirty unrelated file merges; a report touching the same tracked team file or adding the same new one is refused, keeps its branch, and the message says to commit the team files and integrate again.
- This repository carries OrgAI's own team under `.orgai/` since dev 1db0c9a6 (13 roles, 11 skills, 6 servers). It is the first real consumer of the feature. Line-ending warnings on commit are expected: the digest covers parsed content, not bytes.

How each claim was checked: pure rules by unit tests (`src/main/teamFiles/*.test.ts`). Pulls, branch switches, autocrlf, merge conflicts, tombstones and worktree merges by tests with real git in temp repos, two clones of one bare repo standing in for two computers (`service.sync.test.ts`, `service.review.test.ts`, `runtime/worktreesTeamFiles.test.ts`). A live run's isolation by the mock adapter under RunManager and pure tests (`runManagerTeamFiles.test.ts`, `runManagerLiveOverlay.test.ts`). The app only through the existing mock e2e scripts. Reviewed by reading only. No renderer uses any of it yet. Unverified: real use on two computers, a real remote, macOS and Linux (hook suppression, case folding), file symlinks on Windows (EPERM here, so junctions stood in), packaged builds, an 8 MB git status overflow.

## Conventions

- System certificates (issue #16): `systemCerts.ts` `trustSystemCertificates()` runs at boot after `applyShellPath()` once the single-instance lock is ours (and in `--host inproc` right after taking ownership, `src/cli/inprocHost.ts`) and sets Node's default CA list to the defaults plus the OS store (fail-open), so every main-process `fetch` trusts an inspecting corporate root; no fetch swap, verification never weakened. Windows and Linux read the store synchronously. macOS reads it in a killable child (`process.execPath -e`, `ELECTRON_RUN_AS_NODE=1`, minimal env, `cwd: os.tmpdir()`, 120 s timeout, 8 MB cap, killed when a quit goes ahead (the one before-quit handler) or the in-process host ends; the main thread never reads the store, except in launches with `--use-system-ca`, where `getCACertificates('default')` does; index.ts exits at once if `ELECTRON_RUN_AS_NODE` is set in the main script) and the main thread merges and sets; `systemCertTrust()` is 'pending' | 'applied' | 'unavailable' and `describeFetchFailure` words the TLS hint from it without asserting store trust. Unit-tested with a fake api and fake spawner; the real child script ran on Windows under Electron 45.1.0 through the darwin path (platform injected) and a hang was killed at a short timeout. Unverified: the real macOS Keychain path, a packaged build, a certificate from an OS store reaching `fetch`, a real inspecting proxy, Linux, a real Electron quit.
- Settings deep links scroll with `lib/scrollWithin.ts` (the nearest scroll container only), never `scrollIntoView`, so the window and app shell never shift; e2e checks with `windowShift(page)`. Permission-mode short names come only from `lib/settingsCopy.ts` `PERMISSION_MODE_SHORT`.
- `app:openPath` (ipc.ts `openPathRefusal`): opens only an existing directory (lstat, so a symlink or file is refused) that is a stored project's folder, an entry of a project's `allowedDirectories`, or the data dir or inside it, compared on lexical and real spellings (`scratch.ts` `samePath` / `isInsideEither`); at most 1,024 chars (`OPEN_PATH_MAX_CHARS`), no hidden characters, absolute, not UNC or device. A refusal or an unexpected error comes back as the message string (shell.openPath's contract), never a throw. Unit-tested in ipc.test.ts; symlink and junction refusal and macOS path spellings are not tested live.
- Industry-neutral: built-in roles, prompts and copy name no field of work, and examples come from several fields, never one. The Architect specialises a project from its interview (an engagement's Specialist is renamed there). projectKind tests assert a small list of industry words never appears in the engagement chart or the engagement Architect prompt.
- Reference folders are read-only: every adapter refuses Edit / Write / MultiEdit / NotebookEdit (and Codex file changes) under one before any allow path with `referenceFolderMessage`, and writes one harness transcript row "Refused: <file> is in a reference folder (read only)" (folder in the detail); a `cd` into one asks, alone or in a compound command (`MatchOptions.readOnlyDirs`; nothing touching one is free or covered by a rule, a bare `Bash` rule included). Shell calls: a Bash / PowerShell call is reference-touching when its effective cwd (Claude hook `input.cwd`, Codex `req.cwd`, else the project path, followed through cd / pushd / Set-Location segments; `MatchOptions.effectiveCwd`) is inside a reference folder or any word names a path at, under or above one (quotes removed, both separators, case folded on win32 and darwin, `~` expanded, prefix-safe; `commandTouchesReference`). Such a call never matches a saved or session rule (`shellRulesFor`), gets no suggestion (`chooseSuggestions`), is answered 'ask' with "<folder> is a reference folder: agents may read it, not change it; this command names it" (or "runs inside it"), and carries `PermissionRequest.referenceFolder`. RunManager repeats the guard for every adapter: `requestPermission` drops suggestions and ruleLabels from such a request and `decide` narrows an allow with scope 'session' or 'project' to 'once' (info log), so `permission.resolved` never carries `savedToProject` for it. Reads are not told apart from writes (a `type` / `cat` asks too). A Read / Glob / Grep under a reference folder gets no suggestion. "Always allow for project" never adds a reference folder (or one inside it) to allowedDirectories. Engagements start on permission mode 'default' (`newProject`); the engagement Architect recommends 'default' and proposes 'auto' only on request, saying OrgAI still refuses reference-folder edits and asks before a command that names one. Unit-tested only.
- Keep `npm run typecheck` clean for both tsconfigs. Paths are ./-relative with aliases @shared and @renderer. Never add baseUrl.
- Every type that crosses IPC is defined in src/shared/types.ts and must be structured-clone safe. Wire new IPC in this order: shared types, main/ipc.ts, preload/index.ts and index.d.ts, then the renderer.
- The renderer only consumes normalized RunEvents and ConnectionEvents. Vendor SDK details never leave runtime/<provider>*.ts.
- Adapters contain only event mapping and hook mechanics. Shared behaviour goes in harnessTools.ts, prompts.ts, activity.ts, integration.ts, permissionRules.ts, ruleMatch.ts, network.ts, continuation.ts or usage.ts, and mock.ts is updated to match.
- Settings that can be derived are automatic with an override (self-configuration): an unset Project.maxSubagentDepth / maxConcurrentSubagents, preferEverydayNearLimit or skillEvaluation.enabled means "automatic". Never fill them with defaults in a store, in newProject or in a renderer save; read them only through `effectiveSubagentLimits`, `planGuardOf` / `planGuardEngaged` and `skillEvaluationOf`. Adapters pass the run's own roles (`effectiveSubagentLimits({ ...ctx.project, roles: ctx.roles })`). propose_settings application deletes a stored limit when the approved value equals the automatic one (and ignores non-finite values). projects.json is format version 2: a version 1 file is migrated once by ProjectStore (`dropLegacyLimitDefaults` drops a stored depth 3 / concurrency 8, the old always-filled values; other values stay explicit). - Secrets live only in SecretStore (Electron safeStorage). Covered secrets: the LiteLLM key, MCP env and header values, and MCP OAuth client secrets and tokens.

Overrides (`envOverrides` / `headerOverrides`) are plain text in projects.json and must never hold a credential.

- MCP hardening (from the security pass, unit-tested only):
  - An install answer cannot change the requested id; only name, url, command, args, env, headers, secretEnv, secretHeaders, roles, enabled and description are merged from the card (mergeInstallEdit in runManager.ts); oauth, libraryId and projectOnly are stripped. A run-scoped server resolves only the values typed on its card, never stored secrets or tokens. request_mcp_install is unavailable in setup-like and harness runs.
  - OAuth tokens are bound to the server URL: authorize discards a result whose resource no longer matches, resolve injects the bearer only on a match, and any edit, proposal or promote that changes the endpoint aborts the in-flight flow. The loopback callback answers 400 to any request whose state does not match exactly and keeps waiting. The callback's iss must equal the expected issuer exactly when present, and must be present when the AS metadata advertises authorization_response_iss_parameter_supported; a rejection never exchanges the code.
  - An approved proposal that changes where an existing server points (url, transport, command, args) deletes its stored env and header values and the user re-enters them. A direct user edit keeps them.
  - Connector fields (connectorId, connectorVariant, connectedAt) are written only by the main process (connectors:add and the auth paths). Every other write path (mcp:upsert, mcpLibrary:upsert, installs, proposals, promote) strips them; mcpLibrary:upsert refuses an edit that changes a connector entry's definition, and an approved proposal that does so turns it into a plain entry and drops its OAuth state and tokens. Preset endpoints must be https on public hosts; tokens stay bound to the entry's fixed URL (resource match) even when the `resource` parameter is not sent.

- Git operations on one repository are serialized through worktrees.withRepoLock, which delegates to runtime/repoLock.ts (cli-spec 3.2 (5)). One lock order: (1) reentrancy first: an `AsyncLocalStorage<Map<key, RepoLockLease>>` lease the call chain holds and has not released runs `fn` at once (integrateWorktree(root) -> commitLeftovers(wt) / discardWorktree(root)); (2) the in-process queue of the repository, then the cross-process dir mutex `<commonDir>/orgai-repo.lock` (mkdir, `owner.json` `{ pid, processStartTime, hostInstanceId, acquiredAt, token }` written by rename, mtime heartbeat every 2 s, wait polled every 100 ms and bounded at 60 s with `RepoLockTimeoutError`); (3) `fn` under a fresh lease, `lease.released = true` in finally, so detached work that outlives the scope queues again. A lock dir is reclaimed (rename to `.stale-<uuid>`, then removed) when its owner pid is not live and its heartbeat (newest mtime) is older than `heartbeatStaleMs` (default 4 x heartbeatMs; a holder in another PID namespace keeps beating, review M7), when owner.json is missing or corrupt and the dir is older than 2 s, or when it names this process and host instance but no lease holds it; the reclaim then reports (console.warn and `configureRepoLock({ onRecovery })`) any `<commonDir>/index.lock`, `<commonDir>/worktrees/*/index.lock` and MERGE_HEAD it finds and never deletes them, and puts the notice on the new lease (`repoLockRecovery()`). Inside the lock, integrateWorktree (target and worktree), commitLeftovers and discardWorktree (worktree) check the checkout's git dir for index.lock, MERGE_HEAD, CHERRY_PICK_HEAD, REVERT_HEAD, rebase-merge and rebase-apply before any git command and, when one is there, run none (no merge --abort, worktree remove --force, branch -D, add or reset): integrate settles 'conflict' with a message naming the files and the reclaimed lock (so WorktreeIntegrator logs it and notifies the orchestrator), commitLeftovers returns an error, discardWorktree throws `UnfinishedGitStateError` (MaintenanceService answers ok: false). A path outside any repository gets the in-process queue only. `repoLockActivity()` counts waiters plus holders (for the Wave 1 host's activity tracker). integrateWorktree, commitLeftovers, discardWorktree and prepareRepo take it; `WorktreeIntegrator.exclusive()` is always taken outside it, and a merge review waits outside the lock. A worktree and the main checkout of one repository therefore queue behind each other; different repositories never block each other. Liveness comes from host/processInfo.ts: darwin reads `ps -o lstart=` with LC_ALL=C and TZ=UTC so processes with different locales or time zones agree, and polling loops (this lock, the startup mutex) use `isLiveProcessCached` (a matched start time is trusted for 5 s, signal 0 only in between). After the reclaim rename the moved copy is compared with the owner that was judged dead (token, else pid / host / acquiredAt; an ownerless dir must still be old) and put back when another contender took a fresh lock in between (same for startup.mkdir). A throw from the git layer (`RepoLockTimeoutError`, an unwritable owner file) settles the worktree as 'conflict' in WorktreeIntegrator instead of leaving it 'merging'. Verified by unit tests with real git repos (repoLock.test.ts, worktrees.test.ts) on macOS only; the Windows and Linux process start-time checks the reclaim relies on are unverified.

Hot files (src/shared/types.ts, src/main/ipc.ts, src/main/runtime/runManager.ts, src/preload/index.ts, src/shared/defaults.ts, .orgai/ARCHITECTURE.md, CLAUDE.md, package.json) take one claim at a time.
